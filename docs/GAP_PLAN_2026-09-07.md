Written while assembling `PAPER_2026-09_The_Crossing_Scales.md`. Every item is either
**done**, **queued** (a script exists and is chained), or **open** (costed, not started).
Nothing here is aspirational: an open item carries the runs and the hours it needs.

The paper's claims and what each rests on (updated 2026-09-08 after E35 landed):

| claim | evidence | status |
|---|---|---|

## 1. Defects

### 1.1 Fixed on this branch, with tests that fail against the pre-fix code

**D1 — `tokens_seen` restarted on resume.** `nanolab/train.py` restored `start_step`
from the checkpoint and then re-zeroed the token counter, so a resumed run wrote a
`tokens` axis that restarted mid-file while `step` kept climbing, and `done` reported
the post-resume count as the run total. Blast radius **2 of 1,099 CE runs**
(`cx32lad1536_w1536_attention_lr80_s1337` and `_s42`, each 3050 steps recorded as
25.41M tokens). `final_val` unaffected — every loss table in the repo stands.

Fix: `tokens_seen` now travels with `step` in the checkpoint blob, and a checkpoint
written before the fix is reconstructed exactly by `_tokens_through(cfg, start_step)`,
which sums the schedule rather than multiplying, because a seqlen curriculum makes the
per-step token count a function of the step.
Tests: `a_resumed_run_continues_the_token_axis_instead_of_restarting_it` (reproduces the
defect exactly — `token axis went backwards on resume: [384, 512, 128, 384, 640, 768]`)
and `tokens_through_sums_the_curriculum_rather_than_multiplying_by_block_size`.

**D2 — the `arm` column in the MQAR ledgers is not a key.** `run_one` gained an explicit
`arm` argument partway through the program; before that it fell back to `cfg.mixer`,
which for a hybrid is its recurrent half. **165 committed rows** are filed that way —
`hybrid_mingru10_attn2` as `mingru` (90) and `hybrid_gdn_periodic` as `gdn` (75).
Grouping on that column pools each hybrid into the pure arm it was built to beat.

Fix: `mqar_suite.arm_of(record)` parses the arm from the run name, which has always
carried it, and is now the one way to ask. `board()` already grouped on the name, so the
suite's own printed boards were never wrong; the column misled external analysis.
Tests: `the_arm_of_a_recall_record_is_read_from_its_name_not_its_arm_column` and
`every_committed_recall_record_resolves_to_a_registered_arm`, which reads the committed
ledgers rather than a constructed example — the fallback is invisible unless something
checks the real corpus. All 922 run names resolve to registered arms.

Suite: **178/178 passing, 3 skipped.**

### 1.2 Found, not fixed — each needs a decision before it is touched

**D3 — resume replays one optimizer step.** `tokens_seen` is incremented before the
checkpoint is written, so the saved `step` names an update that already happened, and
`range(start_step, max_steps)` executes it again. Surfaced by D1's test, which now pins
the slack at exactly one step rather than asserting the ideal total and hiding it.
Fixing it means saving `step + 1` as the resume point, which changes what every resumed
run does. **Decision needed**: it is a one-line change with a behavioural blast radius,
and no result in the repo depends on it (2 resumed runs, both complete).

**D4 — one experiment can appear as two cells.** `block_size` is recorded in the newer
MQAR ledgers and absent from the older one, so grouping on it fragments a cell.
`block_size` is derived (`4 * n_pairs - 1`). Any analysis should group on
`(n_pairs, batch, steps, effective_lr)`. Not yet enforced anywhere in code.

**D5 — two ledger files can hold the same run name.** `mqar_e16`/`mqar_e16_board` share
75 names and `mqar_e28_p8`/`mqar_e8` share 60. Worse, **30 of the SWA duplicate pairs
carry different recall values under the same name**, so the name does not identify the
recipe there. Concatenating ledgers is a trap with no guard. A `--report-only` pass that
refuses divergent duplicates would close it.

**D6 — `lock_recipe` still waves through `device` and `gpus`.** Carried over from
2026-09-05; no artifact records what an old suite ran on, so a guessed legacy default
would refuse good directories. Unchanged, still open.

### 2.2b G7's result, and what it broke — 2026-09-08

**G7 DONE 18:39:25Z**, exit 0, 4.65 h, 30 new runs into `crossover50m_ratioplace32`.
It answered its own question favourably and broke a larger one.

**The LR argmin reverses with horizon, and it reverses for attention too.** At w768/50M,
`final_val` rises monotonically with learning rate for every arm on the board:

| arm | 1x (6e-4) | 4x | 8x |
|---|---|---|---|
| `attention` | **4.2181** | 4.3487 | 4.4732 |
| `hybrid_mingru8_attn4` | **4.2016** | 4.3760 | 4.4958 |
| `hybrid_mingru_periodic` | **4.1939** | 4.3776 | 4.5013 |

Paired: 4x is +0.1306 worse than 1x (0/5 seeds), 8x is +0.2551 worse (0/5). The 10M probe
had the **opposite** order at the same width and shape — 1x 5.3608, 4x 5.2102, 8x 5.1663.
Not a board artifact: `crossover_ladder50m`'s `w768_attention_lr80` is 4.4702 against this
board's 4.4732, **0.0030 apart** — at the 0.0031 floor, across two boards at different
tenancies.

`scripts/e21_ladder_probe.sh` predicted this in its own header when it was written: *"the
best LR at 10M is not guaranteed to be the best at 50M, so phase 2 inherits an assumption
rather than a measurement."* It does not hold.

**Cost to sections 3 and 4.** The ladder spent 50M at LRs chosen from 610-step runs. At
w768 that is **0.255 nats** off the best LR measured at 3051 steps. "Each arm at its own
measured learning-rate optimum" is false at the 50M budget, and every crossing in the
paper sits at a mistuned point.

**Credit to section 5.** E35 inferred the hybrid boards were confounded because the
hybrid's argmin (4x) differed from attention's (8x). At 50M the preference order is the
**same for all three arms**, so the 1x boards were not reading arms from different
distances and that inferred confound largely dissolves. The rows are unchanged: 8+4
**-0.0165** [-0.0210, -0.0121], periodic **-0.0242** [-0.0294, -0.0191].

**A new caveat replaces it.** The hybrid lead exists only at 1x. At 4x attention wins by
+0.0272 / +0.0289 and at 8x by +0.0226 / +0.0281, all 95% intervals excluding zero.
Section 5's result holds at the best LR tested and reverses away from it, and must say so.

### 2.2b-ii G3's result — the reversal is not local to w768

**G3 DONE 2026-09-09T00:22:59Z**, exit 0, 5.73 h, 30 new runs into `crossover_ladder50m`.
It was designed to ask whether the argmin moves with horizon and was bracketed, before G7,
on the assumption that it would not move far. Every one of its six grids runs off its
**bottom** edge, at both widths and for both mixers:

| cell | ladder's choice | one step down | one step up |
|---|---|---|---|
| w1152 attention | 8x | 4x: **-0.1254** [-0.1288,-0.1219], 5/5 | 16x: +0.1352, 0/5 |
| w1152 minGRU | 4x | 2x: **-0.1398** [-0.1462,-0.1334], 5/5 | 8x: +0.1525, 0/5 |
| w384 minGRU | 4x | 2x: **-0.0860** [-0.0884,-0.0836], 5/5 | 8x: +0.1229, 0/5 |

Together with G7 at w768 that is **four architectures at three widths, all preferring a
lower learning rate than the ladder gave them, with no exception**. Nothing here is an
argmin: every grid needs extending down, which is G8a.

The curves also show the mechanism rather than just the effect. At w1152, attention's
lr40-minus-lr80 gap is only **-0.0417** at 4.11M tokens (4/5) and widens monotonically to
-0.1254 by 50M. The high LR really is competitive early — which is why the 610-step probe
picked it — and loses over the remaining 2400 steps. The argmin is a function of horizon,
not a constant that the probe measured badly.

### 2.2d G8a — the 50M argmin located, and it is not what the ladder assumed

**G8a DONE 2026-09-09T05:19:58Z**, exit 0, 4.9 h, 36 runs. **Every cell has an interior
argmin**, so for the first time the 50M grid has actually found a minimum rather than an
edge:

| width | attention | minGRU | 8+4 hybrid | 9+3 periodic |
|---|---|---|---|---|
| d384 | **2x** | **2x** | — | — |
| d768 | **1x** | **1x** | **1x** | **1x** |

Two results, pulling in opposite directions:

**The argmin is ARM-invariant.** At d768 all four architectures pick 1x. A shared-LR
board was therefore never reading them from different distances, which **retires the
confound E35 inferred and G7 already suspected was gone**. Section 5's rows at 1x were
at every arm's own optimum all along. G10 now costs **nothing**: its plan resolves to the
three arms already on `crossover50m_ratioplace32` at n=5.

**The argmin is NOT width-invariant.** d384 wants 2x, d768 wants 1x. At 10M it *was*
width-invariant — 8x for attention and 4x for minGRU at all three widths, which is what
the ladder relied on. **Width-invariance of LR transfer holds at a short horizon and
breaks at a long one**, and that is a claim about muP-style transfer rather than merely a
correction to this paper's tuning.

**Consequences, both acted on:**
* G9 was written to let w1536 inherit a multiplier on measured width agreement. There is
  no agreement, so **the inheritance path is removed from the planner entirely** — every
  width is now planned from its own probe — and **G8d** was inserted to give w1536 one.
  Without it the re-tuned width claim would span three rungs and be missing the top one.
* `w768_attention_lr10` restates the base Config, so it trains the *identical* model to
  the bare `attention` arm — and the probe landed exactly on that collision. The planner
  now reuses an equivalent arm the target board already carries, which is what turns G10
  from fifteen duplicate jobs into zero.

### 2.2g G11 — n=3 under every argmin, and the one test that can falsify the law

**Queued 2026-09-09T13:44Z, between G9 and G10.** Two requests that looked separate are
one experiment.

The 1/width law fits `width x lr = 0.4608` at d384, d768 and d1536. **d1152 is the only
width that can falsify it** and the only one where it is untested: the law predicts
lr 0.0004 (2/3 base), and the 2x-spaced grid has only 0.5x (4.1659) and 1x (4.1595) —
straddling the prediction, 0.0064 apart.

The two-job version of that test cannot work. Fitting the d1536 basin — the one measured
on both sides — puts the gain of the true argmin over 1x at **~0.0115**, so the
0.667x-vs-1x gap at d1152 should land near **0.002–0.006 nats**, at or below the 0.0031
rerun floor. At n=1 the answer would be unreadable whichever way it came out. The law's
point needs n=3, which is exactly what the "every argmin is n=1" objection needs too.

So: the argmin and both neighbours at **n=3** at all four widths, plus the new 0.667x
point at d1152. **46 new jobs, ~8.4 h, ~$19.1** — not the ~$10 first estimated, and the
error was mine. Routing is forced by three tenancy locks (d384/d768 at 3, d1152 at 2,
d1536 at 1); the d1536 half is $9.92 of the total because that width cannot share a
device. Widths run cheapest-first, so interrupting drops the expensive one.

Pre-registered: 0.667x must beat **both** neighbours by more than 0.0031 for the law to
be established. Landing inside the floor of 1x means the data is *consistent with* the
law but does not establish it — a flat basin is not a confirmed prediction. Worse than 1x
beyond the floor falsifies `width x lr = 0.4608` at the one width that could, and the
1/width claim comes out of the writeup: three points on a line through two free
parameters is not a law. Any argmin that moves under the extra seeds was never located,
and G9's re-tuned rung for that width retires with it.

### 2.2c Defects found while reading G7 — both fixed, both tested

**D7 — `paired_board.py` refused every per-arm-argmin comparison.** `lr` and `matrix_lr`
sit in `RECIPE_KEYS`, so pairing `w768_attention_lr40` against `w768_attention_lr80`
exited with "recipes differ". G7 could be run and then not read. Fixed at the guard: a
field the **registry declares** as one of the two arms' own overrides is waved through and

declares still refuses. The exemption is per-FIELD, not per-pair — exempting the pair
would have turned a guard into a hole, and the test asserts both halves.

**D8 — `paired_board.py` read curves off the pre-D1 token axis.** Every marker and
crossing in that file is read against `tokens`, which restarted at 0 on a pre-D1 resume
while `step` carried on; `at()` interpolated across the fold silently. Now refused by
name, with the direction to re-read. **Blast radius measured: 2 of 1151 committed eval
curves fold**, both `cx32lad1536_w1536_attention_lr80` (seeds 1337 and 42) — the top rung
of the width ladder. See G8c.

**Checked and clean:** `crossover_ladder1536` records `fused_ce: True` where the other
three rungs predate the field. `LEGACY_RECIPE_DEFAULTS["fused_ce"]` is also `True`, so the
top rung and the rest ran the same way and the width claim carries no fused-CE confound.

## 5. G11's two bugs, and the defect the second one exposed (2026-09-09)

**G11 exited 2 having launched a quarter of its plan and none of the point that
mattered.** Both bugs are recorded here because the second one was, briefly, a false
finding that this document would otherwise have absorbed as a real one.

**Bug 1 — word splitting, in bash.** The cell table was a here-string iterated with
`for row in $CELLS`, and word splitting does not respect lines: each row's trailing
multiplier list `lr05 lr0667 lr10` split into three separate "rows", of which the second
and third carried no colons, so `${row%%:*}` returned the whole token for every field and
the launcher was invoked as `--workers lr0667`. argparse refused it 48 times and exited
2. What *did* run was the first multiplier of each line — **one neighbour per width,
never an argmin, and never the 0.667x law point.** G11b reads its cells with
`while IFS= read -r`, one line at a time, and refuses any row whose workers field is not
a number — the guard that would have caught this one.

**Bug 2 — `lr_argmin.py` averaged over unequal seed sets.** G11's readout then announced
that two argmins had moved: d384 attention 2x→1x and d1152 attention 1x→0.5x. **Neither
had.** Bug 1 had enriched exactly one point per curve to n=3 and left its neighbours at
n=1, and `argmin()` was taking the plain mean of whatever seeds each point carried.

On these boards **seed 100 is the easiest seed at every cell and 777 the hardest** —
4.1229 against 4.1803 at d1152 attention 1x, a **0.0574 spread, 18x the 0.0031 rerun
floor**, where the argmin margins being decided are 0.005 to 0.05. Enriching one point
with seed 100 and not its neighbour therefore moves that point down by more than any
margin on these grids. Both "moves" were the arithmetic of which seeds had been run.

The readout also hid its own evidence: the stage grepped `^  d|argmin`, which drops the
line carrying each point's `(nK)`. A reader would have seen two relocated optima and no
seed counts.

**The fix is structural, not a special case.** `cells()` now returns `{mult: {seed: val}}`
rather than `{mult: [vals]}`, so no caller can average two points over different seed sets
without first noticing they differ. `argmin()` reads the grid on the seeds common to
*every* point, and the margin over the runner-up on every seed those two share — usually
more. It returns the string `"interior"` only for an argmin this rig can defend, and every
consumer already gates on `verdict == "interior"`, so all of them fail closed:

| refusal | when |
|---|---|
| `only N point(s)` | fewer than 3 |
| `EDGE (bottom/top)` | minimum at a grid edge |
| `no seed is common to every point` | the curve cannot be read paired at all |
| `FLAT — … at or under the 0.0031 rerun floor` | margin the rig cannot resolve |

Three assertions in
`an_lr_curve_is_read_paired_by_seed_not_by_whichever_seeds_a_point_happens_to_have`
fail against the pre-fix code, verified by running the real d1152 fixture through it:
it returns `(0.5, 'interior')` where the paired reading returns `(1.0, 'interior')`,
calls a 0.002-nat basin `interior`, and answers `EDGE (top)` on a curve with no shared
seed at all. 186/186 on the box.

**Read paired, the 50M argmin table is exactly what was reported before G11 ran** — all
eight cells interior, both mixers agreeing at every width:

| width | argmin | lr | width x lr | tightest paired margin |
|---|---|---|---|---|
| 384 | 2x | 0.0012 | 0.4608 | 0.0167 (vs 1x) |
| 768 | 1x | 0.0006 | 0.4608 | 0.0393 (vs 0.5x) |
| 1152 | 1x | 0.0006 | 0.6912 | **0.0047 (vs 0.5x, 3/3 seeds)** |
| 1536 | 0.5x | 0.0003 | 0.4608 | 0.0085 (vs 1x) |

d1152 remains the one row that breaks `width x lr = 0.4608`, and its margin is the
closest on the ladder — 1.5x the floor. The law's prediction there is 0.667x, which lies
between the two points being compared. **That test has still never run.**

### G11b — the repair, ~22 runs, ~4.9 h, ~$11.2

Chained `g9b → g11b → g10 → g4 → g5 → g6 → g8c`, one waiter per link.

1. **d1152 at 0.667x, seeds 1337/42/100** — the law's one unverified point, pairing
   against 0.5x's three seeds and 1x's five.
2. **n=3 under each width's argmin** — G11 left every width with n=3 at a *neighbour* and
   n=1 at the argmin, which is the wrong way round. Seeds 42 and 100 go at d384 2x,

falsified at the one width that could falsify it, and the 1/width claim comes out of the

## 6. The 2026-09-09 stage cascade: one timeout, two stages (and the law result)

**`stage_wait` gave up after `PREV_HOURS` and printed "starting anyway".** g10's marker
never came — it was queued behind g11b's ~5 h run — so at 22:31:17Z g4 started anyway,
onto a GH200 already carrying g11b's workers. All four of g4's MQAR workers died of CUDA
OOM (`220.00 MiB free`, four foreign processes named in the traceback). g4's own exit
marker then released g5 at 22:32:41Z, which launched into the same contention and lost
**12 of its 18 family arms** to OOM and `CUBLAS_STATUS_ALLOC_FAILED`. g5's marker then
released g6, which ran ~30 min concurrently with g11b's exclusive-tenancy w1536 board
before being killed.

**This is the repo's own rule violated by its own harness:** *a check that could not run
must never report the same result as a check that ran and passed.* A wait that timed out
proceeded as though the predecessor had finished.

**Fix — the marker is a hint, the device is the fact.** `stage_wait` now does both:
an overrun on the *marker* is loud but non-fatal (a wedged predecessor should not hang
the chain forever), while a *device* still carrying compute PIDs refuses the launch
outright and the stage writes its own `exit=75` marker so the chain drains as refusals
instead of stacking workers. `DEVICE_WAIT_HOURS` (default 24) bounds that wait; `0` means
do not wait at all. The guard is inert unless callers check it — there is no `set -e` —
so all 22 stage scripts moved to `stage_wait || stage_refused NAME`.

`a_stage_never_launches_onto_a_gpu_another_stage_is_still_using` covers both directions
with a stubbed `nvidia-smi`, and asserts that no `scripts/*.sh` calls `stage_wait`
without checking it. It fails against the pre-fix code, which returns 0 on a busy device.

**Damage, measured rather than assumed:**

| stage | lost | recoverable |
|---|---|---|
| g4 | all 4 workers, 0 runs written | yes — full rerun |
| g5 | 12 of 18 family arms; **6 completed and are valid** | yes — `job_done` requires an actual `done` record, so the 12 rerun and the 6 are skipped |
| g6 | 1 run dir, **0 `done` records** | yes — nothing completed at shared tenancy |
| g11b | **nothing — zero errors** | n/a; it held its allocation and won the collision |

**Correction, same night.** The line first written here — *"co-tenancy costs wall-clock
and risks OOM; it does not change the arithmetic of a run that completes, so g5's 6
survivors are usable"* — **is wrong**, and wrong in the way this document keeps warning
about. `docs/GPU_TUNING_2026-09-05.md` §4 already names co-tenancy as *"the one place
tenancy changes what a job trains on rather than merely how it is scheduled, and it fails
silently"*, and that applies here.

`data.should_gpu_resident` returns True unconditionally only below
`_GPU_RESIDENT_MAX_TOKENS` (150M). **This repo's train split is 497.5M tokens**
(`nanolab/data/HuggingFaceFW_fineweb-edu/train.bin`, 995 MB of uint16), so the branch
that runs is the one that consults `torch.cuda.mem_get_info()` and requires
`1.85 GiB < 0.2 x free`, i.e. **free > 9.27 GiB at Batcher construction**. Below that the
run silently takes the memmap path, which samples with a **CPU** generator where the
resident path uses a **CUDA** one — the same seed, a different token stream. The fallback
needs *less* VRAM, so it converts an OOM into a run that finishes and looks ordinary.

**Nothing on disk recorded which path a run took.** That is now fixed:
`Logger.banner(sampler=...)` writes `"sampler"` into every run's `start` record —
`gpu_resident`, `memmap`, or `"unknown"`, because a run whose path cannot be established
must not look like one that took the fast path. Test:
`every_run_records_which_sampler_path_it_took`.

**Exposure, measured rather than assumed.** `mean_tok_s` separates solo from co-resident
but *cannot* separate resident from memmap — a degraded rate is equally consistent with
either — so it is used only to clear runs, never to condemn them:

| run | mean_tok_s vs cohort median | reading |
|---|---|---|
| `cx32lad50_w1152_mingru_lr0667_s100` (law test) | **209%** — fastest of 27 | ran solo; **clear** |

**The d1152 law result is unaffected** — all six of its runs are the fastest in their

### 6b. The repair destroyed the evidence for the thing it repaired

Relaunching g4, g5 and g6 by hand at 00:31 used `nohup ... > nanolab/out/g4.log`, which
**truncates**. Those three files held the only copy of the cascade: g4's CUDA OOM

This is the rule G8c states and follows, broken while applying it: *the corrupted records
are the evidence for a defect this document reports, and overwriting evidence to make a
caveat go away is not the same as measuring it away.*

Appending would be worse rather than better. `stage_wait` greps `^<stage> exit=` out of
`nanolab/out/<stage>.log`, so a marker retained from a previous attempt releases the next
stage the instant it starts waiting — the g4/g5 cascade again, from the opposite
direction. The old log has to leave that filename, not sit at the top of it.

`scripts/relaunch_stage.sh NAME [PREV] [PREV_HOURS]` now rolls a non-empty log to
`nanolab/out/NAME.<timestamp>.log` before launching, reports how many bytes it preserved,
and resolves the script by name so the stage cannot be relaunched against the wrong file.
`relaunching_a_stage_preserves_what_the_failed_attempt_recorded` asserts all three
properties, including that the live log carries no stale `exit=` marker afterwards.

**Use it instead of a hand-written `nohup` line.** Every relaunch in this program so far
has been hand-written, and this is what that cost.

### Two defects, both of which made work invisible

**1. `lock_recipe` refused a no-op (`crossover_replicate.py:1172`).** The arms-may-grow
seam tested `set(old) < set(rec)` — a STRICT subset. G5 and G10 each built their arm list
as *everything on the board* + *everything I plan to run*, so when every planned arm was
already present, `set(rec) == set(old)`, the test was false, and the lock refused on
`conflicting fields: ['arms']`. **G10's exit=1 was this and nothing else. G5's family
probe never launched a single job because of it.**

Fixed at the canonical owner: `arms` is deduped, order-preserving, before anything
compares it — a set wearing a list's clothes, and re-adding an existing member asks for
nothing. Shrinking and diverging still refuse. Test:
`re_adding_an_arm_the_board_already_carries_is_not_a_recipe_conflict`, four cases, fails
pre-fix with the exact original error.

**2. The queue kept vouching for runs that were not there.** With the lock repaired, G5
launched cleanly and still ran nothing: `pending 0`. Its queue held 12 entries stuck at
`failed` from the OOM cascade — a terminal state nothing clears, since `--unhold` releases
only *held* jobs — and **6 marked `done` whose directories had since been quarantined**.

That second group is the sharper defect and the same one this document keeps finding: a
queue entry claiming `done` for a run with no data is a check that could not run
reporting the same result as one that ran and passed.

`scripts/requeue_incomplete.py SUITE [--apply]` reconciles the queue against disk — any
entry without a real `done` record in `metrics.jsonl` returns to `pending`, stale
worker/detail metadata stripped; a run whose metrics DO carry the record is left alone
whatever the queue claims. The artifact wins over the claim, never the reverse. Dry-run by
default. It found exactly 18 on `crossover_probe50m`, matching an independent count.

### G4 and G6 — not run, and why

**G4** OOM'd on its **own** workers this time, not a cascade: 4 × 23.5 GiB on a 94.5 GiB
card. `--workers 4` is simply over-subscribed for the MQAR p128/b128/seq511 cell; it needs
2. It reached 8 solved of 29 started, and the first hybrid arm solved recall 1.000 at
seq 511 — one seed, not a result, but the first evidence on the axis E36 left open.

**G6** refused correctly. Its w1920 probe OOM'd on `mingru_lr40`, so it declined to plan
the d1920 rung rather than plan on a broken grid. The guard doing its job.

### Mamba-2 has no fused scan on this box — measured

G5's Mamba-2 arms run at **10.6K tok/s, 0.9% MFU** at w768/workers 3, against **30.5K**
for MLA and **14.7K** for GDN on the same board at the same tenancy. That is ~3x slower
than MLA and puts one 50M-token Mamba-2 run at ~79 minutes.

It matters for costing, not just curiosity: the family probe was budgeted as "roughly the
ladder again" on the assumption that all three families cost about what attention costs.
They do not. **18 arms is ~978 run-minutes, ~5.4 h at tenancy 3 — not the ~2.5 h a
uniform-cost estimate gives.** Any future re-ladder of these families should be priced
per family from these numbers.
