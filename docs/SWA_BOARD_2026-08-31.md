# The sliding-window board — E12 / E15 / E16, and the gap none of them closes

Written 2026-08-31 after reading *Sliding-window beats linear attention*
(arXiv:2608.28444, Jolicoeur-Martineau, Sukthanker, Cameron, Gervais). Continues
`EXPERIMENT_BACKLOG_2026-08-26.md`; E13 and E14 there are taken, so the two new
items are **E15** and **E16**.

## What the paper claims, and which half this repo can test

The paper masks a **pretrained** model at inference: SWA(w, s) attends to the `s`
first positions (StreamingLLM sinks) plus the `w − s` most recent, primarily
SWA(64, 4). It reports that this training-free swap matches or beats
**post-trained** linear attention, and beats it 2–10× on NIAH and BABILong.

That comparison has two independent parts:

| Part | Testable here? |
|---|---|
| Is a *local-attention* stack competitive with a *linear-attention* stack, at matched training? | **Yes** — E12/E15/E16 below. GDN is this board's linear-attention family, already at n=5. |
| Can you *retrofit* a pretrained model, training-free, and beat a post-trained retrofit? | **No.** See "The gap that renting a GPU does not close". |

Everything below answers the first. Nothing below answers the second, and no row
produced by these suites should be quoted as if it did.

## E12 — sliding-window attention arm (ctx 512) — **code complete, unrun**

Closes the backlog's own E12, which was `status: needs code`. That entry asked
for "a `window_size` option on the existing attention mixer implemented as an
attention mask, then two arms — `swa` and `hybrid_mingru10_swa2` — against their
global-attention twins", and noted it is "only interpretable after E8 exists".
E8 now exists (360 runs), so it is unblocked.

`nanolab/mixers.py` gains `sliding_window_mask` and a `swa` registry entry that
is `Attention` plus a mask and nothing else — same GQA, RoPE, QK-norm, gating,
value residual, and **identical parameter count** (123,699,612, asserted in
`nanolab.tests`). Sinks are sequence positions, not learned logits.

Stage `swa32`, recipe identical to suite 26 in every field, own out dir. Arms:

| arm | config | question |
|---|---|---|
| `swa_w64` | SWA(64,4) | the paper's primary |
| `swa_w128` | SWA(128,4) | the backlog's choice — "window 128 so the window binds" |
| `swa_w256` | SWA(256,4) | ½ of context |
| `swa_w64_nosink` | SWA(64,0) | isolates the sinks, the paper's load-bearing part |
| `hybrid_mingru10_swa2` | mingru×10 + SWA(128,4)×2 | **must the hybrid's attention be global?** |

The sweep's top endpoint is free: at ctx 512 a 512-wide window *is* full causal
attention, i.e. the `attention` arm already at n=5.

## E15 — the same arms at context 2048 — **code complete, unrun**

Stage `swa2k`, on E9's recipe exactly (batch 8 × ctx 2048 = 16,384 tokens/step,
suite 26's cadence). Windows 64/256/512 span 1/32, 1/8, 1/4 of context.

E15 exists because **E12 alone would understate SWA**: at ctx 512 a 64-wide
window already spans 1/8 of the sequence and there is almost nothing for locality
to save. Measured at 12L/768d ctx 512, SWA(64,4) is only 6% cheaper in counted
FLOPs than full attention (798.8M → 749.3M per token) and equal in wall clock
within noise. The paper's speed and memory claims live at long context; this is
the axis on which they are even in principle visible here.

## E16 — MQAR across sequence lengths that straddle the window — **code complete, unrun**

**E8's grid cannot test SWA at all.** It runs at `block_size` 15 (`4·pairs − 1`
at pairs=4); a 64-wide window spans that entirely, so `swa` there *is*
`attention`. E16 adds cells that bracket the window:

| pairs | seq | vs a 64-wide window |
|---|---|---|
| 16 | 63 | **control** — window spans the sequence, so `swa_w64` ≡ `attention` exactly |
| 64 | 255 | 4× the window |
| 128 | 511 | 8× the window; only the sinks reach back |

Arms: `attention`, `gdn`, `mingru`, `swa_w64`, `swa_w64_nosink`. 15 seeds, so the
solved-rate keeps E8's binomial (Wilson) interval rather than a t-interval over a
bimodal sample.

**Two properties of this probe, stated rather than buried.**

1. *Sequence length is also difficulty.* More pairs means more to store. The
   SWA-vs-GDN comparison is therefore valid **within** a cell, where every arm
   faces the same difficulty. A trend read **across** cells cannot separate
   distance from difficulty — the axis PAPER §6.8 already reports as
   difficulty-dependent.
2. *Batch decides whether the head forms at all.* E8 measured 0.55 at batch 32
   and 1.00 at batch 256 from the same model. That threshold moves with sequence
   length, so E8's calibrated 256 does not transfer to a 511-token cell by
   assumption. `--calibrate` finds the smallest batch at which the reference arm
   saturates per cell and **refuses** to report a cell where none does. A cell
   run uncalibrated would score every arm ~0 and read as "SWA fails at long
   range" when it means "nothing was trainable here".

## Running it

```
python -m nanolab.crossover_replicate swaboard
```

Phases in dependency order, each resumable (`--from`) and individually runnable
(`--only`), each idempotent on its own artifacts:

`probe → swa32 → swa2k → mqar-calibrate → mqar-grid`

**Run the probe.** On CUDA an explicit `attn_mask` cannot use the flash kernel.
The memory-efficient backend does support masks and should not materialise the
score matrix, but that was verified on MPS, not CUDA — and a fallback to the math
path at ctx 2048 would OOM the stage. The probe measures real tok/s and peak
memory at both contexts in ~15 minutes and turns every range below into a number.

### Cost, from measured anchors

Anchors, all from this repo's own GH200 artifacts: `cxwc_attention` 11.4 min/run
at 50M/bs32/ctx512 single-tenant (n=5); `cx2k_attention` 17.3 min/run at ctx 2048,
workers=2 (n=5); `mqar_e8` attention 159 s/run at 3000 steps, seq 15 (n=45).
GH200 on-demand $2.29/GPU-hr. Ranges span SWA = 1.0–1.4× attention.

| phase | runs | jobs/GPU | 1x H100 SXM5 | 8x A100 |
|---|---|---|---|---|
| preflight probe + calibration | ~15 | 1 | 1.3–4.0 h | 0.5–1.6 h |
| E12 `swa32` (7 arms) | 35 | 2 | 5.2–7.2 h | 2.0–2.8 h |
| E15 `swa2k` (6 arms) | 30 | 2 | 5.2–7.3 h | 2.0–2.8 h |
| E16 seq 63 (control) | 75 | 4 | 2.7–6.7 h | 1.0–2.6 h |
| E16 seq 255 | 75 | 4 | 6.7–20.0 h | 2.6–7.8 h |
| E16 seq 511 | 75 | 4 | 15.6–48.9 h | 6.1–19.1 h |
| **total** | **305** | | **37–94 h · $157–404** | **14–37 h · $319–820** |

The GH200 this was first costed for is out of capacity. H100 SXM5 shares its die
class, so the kernels, the SDPA backend selection and the numerics are the same;
H100 PCIe is a lower-clocked part at 0.76x and lands at the *same total cost*
while taking 30% longer, so it is strictly dominated.

**Cost is rented wall clock, not summed job-hours** — one GPU costs its hourly
rate for each hour it is up, however many jobs are on it.

**Jobs-per-GPU has sharply diminishing returns; GPUs do not.** Measured on one
device this session: aggregate throughput 1.00 / 1.29 / 1.49 at 1 / 2 / 4
concurrent processes, which agrees with this repo's own GH200 note ("~1.8x
faster single-tenant than three-to-a-GPU", i.e. 1.67x aggregate at three). An
earlier version of this table divided wall clock by the worker count, which
assumed linear scaling and was wrong by roughly 2.7x at four workers. Adding
GPUs *is* linear — the board is 305 independent runs — which is why
`--gpus` exists.

Before the optimisation pass, and on the GH200, this board was 45–125 h.

The E16 multipliers are extrapolation from a 15-token cell, not measurement —
which is what the calibration phase exists to replace. The seq-511 row is both
the largest and the least certain; it is also the only cell where a 64-wide
window is an 8× reach.

## Optimisation pass (2026-08-31, before any run)

Two things were measured and changed; a third was measured and rejected.

**Rejected: `flex_attention`.** Numerically exact (2e-06) and its BlockMask
reports 82% sparsity at ctx 2048, but it needs `torch.compile` to be fast and
these suites run `compile=False` by design. Compiled, it measured **39.3 ms**
against the dense mask's 18.9 ms on Apple silicon — its Triton path targets
CUDA, which is untestable here. Adopting it on a benchmark showing a 2x
regression on the only hardware available would have been guessing.

**Kept: exact chunked SWA** (`swa_chunked`, `swa_auto_chunk`). A chunk of
queries can only reach `chunk + window` keys, so the other keys' scores are
never formed — versus the dense path, which computes all T² scores and discards
97% of them. Measured **forward+backward** (forward alone gives the wrong answer
and picked the wrong chunk size, because the chunked path builds T/c times as
many autograd nodes):

| shape | causal | dense window | best chunk |
|---|---|---|---|
| T=2048 W=64 | 196 ms | 178 ms | **86 ms** (c=256) |
| T=2048 W=512 | 186 ms | 194 ms | **122 ms** (c=512) |
| T=512 W=64 | 51 ms | 51 ms | **45 ms** (c=256) |
| T=512 W=256 | 50 ms | 50 ms | 56 ms — chunking **loses** |

Hence `chunk when T >= 4*window, at c = max(256, window)`, which picks the
fastest cell in all four and declines the one where chunking loses. Note the
dense path at T=2048/W=64 was *slower than full causal attention* — a "cheap"
mixer costing more than the baseline it exists to beat.

End-to-end on the 124M model the gain is batch-dependent and only partly
demonstrable here: 1.09x / 1.12x / 1.15x at batch 1 / 2 / 4, rising as the
attention term grows against fixed overheads. `swa2k` runs at batch 8, whose
isolated attention shape (B8 H12 T2048 D64) is the 2.06x row above; the bs8
model measurement on this hardware is contaminated by memory pressure and is not
quoted. **The end-to-end figure at the real batch is predicted, not measured** —
`probe` re-measures both paths on the box and prints which to pin.

`swa_chunk` is numerically identical either way (asserted end-to-end in tests),
so it never moves a quality row; it moves throughput by up to 2x, so it is a
recorded recipe field and `SWA_CHUNK` pins it.

**Kept: worker parallelism for E16.** The 225-run grid executed in one Python
loop. These are 9.5M-parameter models, and E8's own artifacts put a seq-15 run at
~72K tok/s — under 1% MFU, i.e. a GPU idle between kernel launches. `--workers N`
shards round-robin (not in contiguous blocks: E8 measured GDN at 275 s against
attention's 159 s on the same cell, so a block split hands one worker every slow
arm) and the workers share one ledger by atomic line-append. This is the board's
single largest cost lever, and it is the one part of this pass whose gain is
**inferred from E8's MFU rather than measured on the target**.

**Measured and rejected as a target: the MQAR data generator.** It calls
`torch.randperm` twice per row per step — 512 CPU calls per step at batch 256 —
which looked like the bottleneck. It is not: 1–4 ms/step, i.e. 3–11 s of a
3000-step run, under 2%. Vectorising it is also *slower* at 128 pairs. Left
alone.

### Second optimisation pass: five hypotheses, none shipped

Recorded because a negative result that is not written down gets re-measured.
All figures are medians on Apple silicon at the suites' real shapes.

Where the board's time actually goes, measured per arm in E16's dominant cell
(seq 511, the phase that is ~45% of the whole board on an H100):

| arm | ms/step | vs attention | share of the cell |
|---|---|---|---|
| gdn | 2429 | 3.13x | **45%** |
| attention | 775 | 1.00x | 15% |
| swa_w64 | 747 | 0.96x | 14% |
| swa_w64_nosink | 746 | 0.96x | 14% |
| mingru | 668 | 0.86x | 13% |

So GDN is roughly 30% of the entire board, and it is where four of the five
hypotheses were aimed.

1. **Fused cross-entropy during MQAR training.** `fused_ce=False` is set for the
   whole run because `recall_accuracy` needs logits, but the training loop
   discards them (`_, loss = model(x, y)`) and only the final 25-iteration eval
   scores them — 3000 steps materialising a tensor nobody reads. `cfg.fused_ce`
   is read at forward time, so it could have been toggled. Measured **1.02x /
   1.00x / 0.99x** at the three cells: MQAR's vocabulary is ~1025, so logits
   never dominate. Fused CE pays at 50K vocab, not here. The existing comment is
   correct; left alone.

2. **GDN chunk size.** `mixer_chunk` defaults to 64. Swept at seq 511: c=128 is
   **1.09x**, c=256 is 1.01x, c=32 and c=16 are worse. Rejected: 9% on 45% of one
   cell is ~4% of the board, and it moves the loss (6.51545 -> 6.51282), which
   means changing a recipe field E8's completed runs used at the default.

3. **`torch.compile` on GDN.** `mixer_needs_eager` has excluded it since before
   the current kernel, so the claim was worth re-testing. It does not compile at
   all: `linalg_solve_triangular` in the chunked kernel fails an inductor stride
   assertion. The exclusion stands.

4. **`swa_auto_chunk` mistuned for E16.** The rule was fitted at 12 heads and
   ctx 2048; E16 runs 4 heads at seq 511, so it plausibly picked wrong. It did
   not: dense 772.9 ms, c=128 754.3, c=256 757.6 — everything within 2%, and the
   rule's pick is 0.4% off the best. The model simply is not attention-bound at
   d=256 with 4 heads.

5. **Caching the per-chunk masks in `swa_chunked`.** They are rebuilt every
   layer, every step. Measured at **0.8%** of a fwd+bwd call (0.59 ms of 75.0),
   i.e. ~7 ms per 12-layer step. Not worth the cache state.

The conclusion is that the first pass took the available wins — chunked SWA at
long context, worker sharding, and multi-GPU — and these shapes are now at their
floor in pure PyTorch. Further GDN work means a fused CUDA kernel from
flash-linear-attention, which is a new dependency and a numerics change, and is
not worth it for a board whose readout is a solved-rate.

## Hardware: what moves with the box, and what must not

Every suite in this repo was measured on a GH200. These will not be, so two
things changed.

`PEAK_FLOPS` defaulted to GH200's 989.5e12 at four call sites. On any other card
every MFU printed would have been silently rescaled — the defect
`crossover_replicate` already records finding once. It is now resolved from the
live device and **refuses** an unrecognised one; `_mfu_from_toks` degrades to
`nan`, because `0.0%` reads as a slow arm and a guess reads as a fast one.
`measure-peak` settles it with an 8192³ matmul, the way the GH200 row was
settled.

`current_recipe` now records the **device**. Two boxes previously produced
byte-identical `recipe.json`, so `lock_recipe` would have mixed a GH200 suite and
an H100 suite in one directory without a word.

And E12/E15 now carry `attention` and `gdn` **as arms** rather than reading those
rows across from suite 26 and E9. Those references were measured on a GH200;
joining them to H100-measured SWA rows would compare architectures across
hardware, which is exactly the confound this paper is about. Ten extra runs buys
a board that is self-contained on whatever box it runs on.

`--gpus N` pins each worker to one device with `CUDA_VISIBLE_DEVICES`, so every
job still addresses `cuda:0` and the training code, allocator and peak-memory
numbers are untouched. `workers` keeps its existing meaning — jobs **per GPU** —
so no recipe already on disk is reinterpreted; total processes are `gpus *
workers`. Without this, an 8-GPU box bills eight and uses one.

## The gap that renting a GPU does not close

The paper's actual experiment is **training-free masking of a pretrained model**,
benchmarked on NIAH and BABILong against a **post-trained** linear-attention
retrofit (LoLCATs-style). E12/E15/E16 pretrain from scratch. They answer the
from-scratch analogue and nothing more.

Closing the real gap needs four things this repository does not have, none of
which is a compute problem:

1. **A pretrained model of a size where the claim is meaningful.** The paper's
   effects are reported on instruction-tuned LLMs; a 124M FineWeb model has no
   long-context behaviour to preserve. This means *downloading* a 1–8B model, not
   training one — cheap in GPU time, but it puts the work outside nanolab, whose
   whole design is one-variable-per-run pretraining at 124M.
2. **A linear-attention retrofit implementation.** The comparison is against a
   *post-trained* linear model. Without implementing (or importing) that
   conversion and its training budget, "SWA beats linear attention" has no
   opponent — and the retrofit's cost is precisely what the paper's cheapness
   claim is measured against.
3. **NIAH and BABILong harnesses.** Neither exists here. MQAR is a synthetic
   analogue of the same *mechanism* (retrieve a value whose key lies outside the
   window), not the same benchmark, and E16 results must not be reported as
   NIAH numbers.
4. **An inference path for windowed decode.** `Attention.forward_cached` raises
   `NotImplementedError` under a window, deliberately: it attends in full to the
   KV cache, which for an SWA layer would sample from a different model than was
   trained. Training-free inference-time SWA is exactly the path that needs
   window eviction implemented.

Rough shape if it is ever wanted: a separate package, a downloaded base model,
an eval harness pinned to published NIAH/BABILong configs, and a retrofit
baseline. Weeks of engineering, dominated by harness fidelity rather than GPU
hours. **Recommendation: do not start it as part of this paper.** E12/E15/E16
answer a question this board is actually built to answer, and the honest write-up
says so rather than implying the paper was reproduced.
